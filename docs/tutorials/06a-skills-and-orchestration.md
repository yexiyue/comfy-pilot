# 06A · Skills、工具与编排运行时

对应 M2；在 [06 · 上下文工程](06-context-engineering.md) 之后、[07 · 记忆](07-memory.md) 之前阅读。目标：理解 Skills 的作用，并在本项目中划清知识、执行能力与可靠性机制的边界。沿用原有章节编号，本篇是插入的专题。

## LangChain、LangGraph 和 Skills 分别适合什么场景

| 组件 | 核心职责 | 适合的场景 | 本项目的定位 |
|---|---|---|---|
| LangChain | 模型、工具集成与标准 agent 循环 | 快速组装通用工具调用助手，使用中间件调整行为 | 采用 Models、Messages、Tools，初期不使用 createAgent |
| LangGraph | 状态、步骤编排、检查点和人工中断 | 固定业务步骤与模型决策混合，需要持续运行和恢复 | 管理创作生命周期 |
| Skills | 可复用的领域方法、参考资料、模板及可选脚本 | 同一个 agent 按任务加载不同专业知识 | 组织封面设计等创作方法 |
| ComfyUI | 执行图像计算工作流 | 文生图、编辑等已验证的图像能力 | 生成图片的执行引擎 |

LangChain 的 agent 抽象建立在 LangGraph 上。直接使用 LangGraph 时，不必先采用 LangChain 的高层 agent。本项目规划用 LangChain 基础组件配合 LangGraph 自建循环，当前仍是文档阶段。

## 知识与专业术语

**Agent Skill（智能体技能）**是用目录组织的可复用知识包，通常包含 SKILL.md，也可以包含参考资料、模板和脚本。它描述如何完成一类任务，不等于一个独立运行的 agent。

**Skill metadata（技能元数据）**通常包含名称和描述，帮助系统或模型判断什么时候需要读取技能正文。

**Discovery（发现）**是让运行环境知道有哪些可用技能。把目录放在磁盘上并不会让任意 agent 自动认识它。

**Activation（激活）**是在当前任务中选择并加载某项技能。触发规则可以由程序、模型判断或两者共同决定。

**Progressive disclosure（渐进式披露）**是先提供简短目录或摘要，再按需读取正文与关联资料。它减少一开始塞入全部知识的需要，但加载后的正文仍占上下文预算。

**Skill loader（技能加载器）**负责发现、读取及组织技能内容。原生 LangGraph 不会仅因项目出现 SKILL.md 就自动实现完整技能系统；需要应用集成，或采用已经支持它的上层运行环境。

**Tool（工具）**负责真正执行动作。例如“提交生成任务”是工具；“如何选择适合博客封面的构图”是技能中的专业方法。

**Memory（记忆）**记录用户或项目的事实，例如“这个博客使用暖色”。技能描述可复用方法，不应把每次临时偏好写进通用技能。

**Runtime（运行时）**承担实际执行、状态和资源管理。技能携带脚本也需要运行时执行，脚本不会因为被写进技能而自动获得权限。

## 一个完整例子

用户要求：Rust 主题博客封面、右侧留白。

1. 运行时提供可用技能的摘要。
2. agent 或选择逻辑发现“博客封面设计”相关，加载其方法。
3. 将方法与当前 Brief 合并理解，保留用户的明确约束。
4. agent 选择本地已验证的 ComfyUI 工具，提出参数。
5. 程序检查尺寸、工作流可用性和生成预算。
6. 工具执行生成；任务状态和图片版本由应用保存。
7. 用户反馈“保留构图，颜色更暖”，下一轮根据当前基准图和本轮要求重新组织上下文。

技能可以建议检查右侧留白，但不能凭文字证明实际图片符合要求。检查仍需要程序、用户或实际接收图片的视觉模型。

## 适合交给技能的内容

构图原则、风格组织、参考图分析方法、提示词模板、候选图比较标准，以及生成结果不理想时的创作调整思路。

初始练习只需要一项受控技能：博客封面设计。先使用项目内可信、人工维护的内容；不要求技能市场、动态下载或自动改写技能。

## 需要程序保障的内容

允许执行哪些工具、参数范围、资源预算、任务持久化、外部任务对账和用户反馈版本校验。技能中写“最多生成三次”只是指导，程序检查才构成可靠限制。

技能内容不能扩大工具权限，也不能将参考资料中的指令自动提升为系统规则。用户对本次创作的明确要求优先于技能中的默认审美建议，但仍受实际能力与程序限制约束。

## Skills 会淘汰 LangGraph 吗？

不能从 Skills 的流行直接推导出运行时会被淘汰。两者解决不同问题，而且基于 LangGraph 的 Deep Agents 已经支持 Skills。

一种可能的变化是：随着模型能力提升，部分细碎的创作分支可以从固定图节点转为通用 agent 循环加技能。是否采用这种方式，应比较质量、成本、可解释性和恢复行为，而不是只看流行程度。

本项目采用少量编排节点组织生命周期，让模型结合技能做创作决策。没有必要把每种配色或风格都变成图分支。未来可以更换 LangGraph，但上下文、恢复、状态和评测知识仍然有用。

## 设计问题

- 一项技能的描述能否让模型区分“生成封面”和“解释某张图片”？
- 用户要纯黑白，技能偏好暖色时，怎样保留用户要求？
- 技能提到的编辑工具不存在时，系统怎样说明能力不足？
- 同时加载两项技能是否造成重复内容或规则冲突？
- 如何记录本轮加载的技能版本，以解释历史结果？

## 练习与验收

先写出一项技能的内容提纲和激活条件，不实现加载器。选择三个任务：应该加载、不应该加载、相关但所需工具缺失，解释各自行为。

之后在实现阶段检查：
- 能观察到本轮加载了什么技能、为什么加载。
- 无关任务不加载全文，相关任务能读取必要资料。
- 用户约束没有被技能默认值覆盖。
- 技能不会自动扩大权限，工具缺失不会被当成执行成功。
- 相同案例比较使用技能前后的约束符合度、上下文量和生成次数。
- 技能更新后，能识别旧运行使用的版本。

## 常见误区

Skill 等于工具；技能越多越好；Markdown 能保证流程一定执行；加载技能就是长期记忆；技能自带数据库恢复；只要采用 LangGraph 就自动支持技能发现。这些都混淆了知识内容与运行机制。
