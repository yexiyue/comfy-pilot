# 06 · 上下文工程
对应 M2。目标：能解释每次模型调用为什么带这些信息。

## 知识与术语
**Context window（上下文窗口）**是模型单次可处理的输入输出容量边界，具体限制取决于模型。
**Context engineering（上下文工程）**是选择和组织本轮所需信息、工具与格式。
**Token budget（上下文预算）**为指令、资料、历史和输出分配容量。
**Selection（选择）**只保留当前任务相关信息。
**Compaction（压缩）**压缩历史，但可能损失细节。
**Offloading（外置）**将大资料保存到外部，按需读取。
**Just-in-time retrieval（按需检索）**在需要时获取具体资料。
**Multimodal context（多模态上下文）**包含实际图片输入，不等于图片文件名。
**Context contamination（上下文污染）**包括过时约束、无关信息和不可信内容混入决策。

## 本项目的上下文组成
稳定行为约束 + 当前简报 + 必须保留项 + 基准图引用或实际图像 + 本轮反馈 + 必要历史决策 + 当前工具定义。

完整聊天、全部图片、工作流 JSON 和执行日志保存在外部。模型不必每次看到全部记录。程序依赖的密钥和服务连接不是应当发送给模型的上下文。

## 关键权衡
压缩提升容量利用率，但不能用摘要取代精确尺寸、资产 ID 和用户确认的硬约束。检索降低输入量，但可能漏检。图片缩略图节约资源，但小细节可能不可见。

## 练习与验收
构造十轮修改，混入已撤销的要求和重复反馈。列出下一轮具体应带哪些信息，逐条说明用途。比较完整历史、简单截断、结构化简报三种策略是否遗漏硬约束。

## 常见误区
上下文管理就是取最后 N 条；RAG 等于全部上下文工程；保存了图片就等于模型已看过；长窗口可以消除信息选择问题。
