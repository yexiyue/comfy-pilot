# 12 · Harness 收口与 Rust 迁移
对应 M5。目标：从框架使用者进阶到系统设计者。

## 知识与术语
**Mechanism vs policy（机制与策略）**：检查点是机制，何时保存什么是设计决策。
**Contract（契约）**约定模块之间的输入、输出和错误语义。
**Adapter（适配器）**隔离框架和外部服务。
**Durability（持久性）**关注故障后信息是否仍存在。
**Compatibility（兼容性）**不仅包括字段，还包括顺序、恢复和错误行为。
**Migration（迁移）**应保留可验证的行为，而非机械翻译语法。

## 本项目 harness 清单
上下文选择策略、工具可用范围、参数校验、任务状态、人工反馈、外部任务对账、生成预算、资产版本、失败分类和评测。这些共同决定可靠性，单一框架不能替代全部设计。

## 迁移次序
先确定需要迁移的原因，再选择独立模块：资产服务、ComfyUI 通信、任务查询或计算。TS 编排通过稳定协议调用 Rust 服务。只有确有必要才迁移整个 agent 运行层。

保存工作流版本、关键参数和测试样本，能够比较迁移前后的行为。TS 的 LangGraph 检查点不能默认直接被 Rust 解释；运行中的任务需要专门迁移或完成策略。

## 设计问题
迁移是为学习、部署、资源占用还是性能？瓶颈是否其实在图片生成？接口返回成功与实际执行成功是否一致？

## 学完的验收
独立讲清一次多轮创作的完整生命周期；选择一个模块给出迁移边界和验证案例；能够解释为什么暂不引入多 agent、自动工作流生成或向量数据库。
