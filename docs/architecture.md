# 系统边界与架构决策

## 概念结构
当前脚手架位于 `app/web` 与 `app/server`，根目录使用 pnpm workspace。前端实际为 TanStack Start，包含 SSR 构建；本文静态页面托管仍是目标方案，尚未实现。开发时前端 3000、后端 3001，通过 `/api` 代理连接。

```text
React + Vite 本地 Web 工作台
   ↕ HTTP 用户动作 / SSE 应用事件
NestJS 常驻应用服务（TypeScript，默认 Express 适配器）
   ├─ LangGraph：创作状态、步骤流转、人工中断与恢复
   ├─ LangChain 基础组件：模型接口、消息与工具
   ├─ 应用策略：上下文组装、校验、预算与任务对账
   ├─ Skills：按需加载的创作方法
   ├─ SQLite 业务存储：任务、决策、外部任务映射
   ├─ 资产存储：图片、缩略图、工作流快照
   └─ ComfyUI 适配层
          ↕ 本地 HTTP / WebSocket
       ComfyUI 队列与工作流
```

LangGraph 的图描述创作过程；ComfyUI 的图描述一次图像计算。一个创作项目可以包含多次 ComfyUI 任务。

## 职责划分
首版采用模块化单体，前后端同仓库；开发时分别运行，发布时 NestJS 提供构建后的页面与 API。ComfyUI 保持独立进程。Fastify 是可替换的 HTTP 适配器，首版使用默认 Express；不额外引入 Next.js、Redis 队列或微服务。

ProjectsModule 管理项目与反馈；RunsModule 管理运行、调度和恢复；AgentModule 封装 LangGraph；ComfyModule 封装外部通信；AssetsModule 管理图片与版本。Controller 处理协议入口，Provider 提供应用逻辑和依赖，应用协议保持框架无关。

API 与后台执行器首版同进程、不同模块。请求先持久化任务再返回 ID，后台领取并执行；SSE 仅订阅事件，断开不能取消任务。服务启动时核对未完成任务再恢复。NestJS 不自动提供持久任务队列或故障恢复。工程规划见 [02B](tutorials/02b-engineering-foundation.md)。

- 模型：解释需求、提出参数与工作流选择、整理反馈。
- 普通程序：参数校验、约束检查、状态持久化、资源限制、任务查询。
- ComfyUI：执行已提交的图像工作流。
- 用户：确认偏好、选定基准图、判断审美及是否接受结果。
- 视觉模型（可选）：观察实际图像，提供可核验的检查意见；不能仅根据提示词声称看过图片。

## 核心对象
| 对象 | 含义 |
|---|---|
| Project | 一次持续创作的容器 |
| Brief | 当前目标、约束和未决问题 |
| Run | 一轮编排执行 |
| GenerationJob | 一次外部生成任务 |
| Asset | 可定位的图片产物 |
| Revision | 图片版本及父版本、修改意图 |
| Decision | 用户选图、接受、拒绝或约束修改记录 |
| Capability | 已验证工作流能做什么、接受什么参数 |

这些是概念对象，不要求首版逐一建表。应用侧 job ID 与 ComfyUI prompt_id 分开管理；在一对多批量输出中，一个 job 可以产生多个 asset。

## 状态与上下文
持久状态保存事实；模型上下文是按本轮需求生成的视图。图片本体不放入每条聊天记录或图状态快照，保存资产引用。需要视觉输入时按模型接口组装相关图片。

LangGraph 检查点负责图运行进度，不能替代图片资产库、业务数据库或外部任务状态核对。浏览器的断线不代表 ComfyUI 已停止运行。

## 初始决策
- 用 TS 学习编排，用已知稳定工作流学习工具边界。
- 单 agent 足够支撑首版；只有独立上下文或明确职责需求时再研究子 agent。
- AI SDK UI 可保留，但 LangGraph 事件需要明确适配，不能假设两套协议天然兼容。
- 长期记忆先记录用户明确确认的偏好，不急于引入向量数据库。
- 优先让用户评价图片，再按需要增加视觉模型检查。
- 图检查点使用能跨进程保留的后端后，才能声称支持服务重启恢复。

## Rust 迁移边界
优先迁移 ComfyUI 适配、任务查询、资产与计算服务；TS 继续承担 agent 决策。通过应用自有的数据协议交互，不暴露框架内部对象作为长期协议。

完整迁移运行层是独立阶段，需要重新验证恢复与中断语义，不能直接把 TS 检查点视为 Rust 可读取的通用格式。

## LangChain、LangGraph 与 Skills 的分工
本项目明确采用 LangChain 与 LangGraph 配合：LangChain 提供 Models、Messages、Tools 基础组件，LangGraph 组织创作任务的状态、分支、中断和恢复。初期自行组织模型与工具循环，不同时叠加 LangChain 的高层 createAgent。这样便于观察上下文如何进入每轮调用，以及工具如何影响状态。

二者可以组合，但不是技术上必须绑定。后续若标准 agent 循环已经满足需求，可以重新评估 createAgent；不为学习堆叠两套重复循环。Skills 提供可复用创作方法，ComfyUI 提供实际图像执行能力。

采用少量节点控制任务生命周期，把构图、配色等灵活判断交给模型和相关技能；参数校验、权限、预算与任务恢复由程序保证。技能不替代运行时，不自动获得工具权限。

Skills 是上下文来源之一：先发现名称和描述，按相关性读取正文，再按需读取参考资料。项目内有 SKILL.md 不代表原生 LangGraph 会自动加载，应用需要明确的加载与记录机制，或采用已支持它的上层组件。首版不要求引入 Deep Agents。

技能版本与本轮加载记录应能关联到运行轨迹。创作偏好仍归项目状态或用户记忆，避免将临时要求写进通用技能。

参见 [06A · Skills、工具与编排运行时](tutorials/06a-skills-and-orchestration.md)。

## 一轮修改如何协作
用户要求“把第二张图改成暖色”：
1. 应用在图状态中确定第二张图的稳定资产 ID，而不是让模型猜画廊顺序。
2. 上下文逻辑整理旧约束、本次修改和相关 Skill。
3. 通过 LangChain 模型接口发送消息与工具定义，获得响应或工具请求。
4. 程序检查参数、工作流能力与预算，工具通过适配层调用 ComfyUI。
5. 应用跟踪外部任务并保存产物，LangGraph 转到等待用户反馈的阶段。

工具定义本身不会执行 ComfyUI，也不会提供任务恢复；必须分别实现执行函数、外部任务跟踪与持久化。

## 记忆机制的归属
| 问题 | 负责部分 |
|---|---|
| 会话内状态与图进度保存 | LangGraph 检查点及持久化后端 |
| 历史消息选择、裁剪和摘要 | 本项目的上下文逻辑；按接口适配可用组件 |
| 跨会话偏好存储 | 应用长期存储，可评估 LangGraph Store |
| 什么值得记住、何时检索 | 应用策略，必要时让模型参与判断 |

LangChain 文档中的部分记忆中间件面向 createAgent；自建图时不能假定它们自动生效。学习概念后按当前循环明确接入，避免把数据库保存等同于模型已获得信息。
